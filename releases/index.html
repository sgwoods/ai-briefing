Release notes

Running v0.2.0-beta. Changes are built and tested on a development branch and reach production together as a release.

v0.2.0-beta · 2026-10-23

  • Steven's takes (My takes, phase 1): the owner's own view in the edition, verbatim, labelled "Steven's take".
  • Once the edition is written, a private "AI Briefing · Your takes" email lists slots: 0 (the day), T (Top of mind), and 1 to N (each Must-read story). Reply "1: ..." from a phone; "done" sends early, "skip" means none.
  • Your own words on a link you post in the team Slack channel count as your take on that story.
  • The edition waits until 09:15 or "done" (./np takes done, or takes-done in the run queue).
  • Each take is checked for private names, owner addresses, personal links, disclosure phrases and the confidential marker. One that fails is held back and listed to you, never published.
  • Takes appear on the site and in the email, and the host reads each one after its story in the podcast. Only the briefing audio is re-rendered.
  • Retries leave a waiting run alone; a failure ships the edition without takes.
  • ./np takes status | email | preview | done.
  • Fix: the Slack reader closed or leaked its HTTP client when it found your own LinkedIn posts.

v0.1.14-beta · 2026-10-23

  • First-lines check for the daily briefing: the day in brief and Top of mind are now checked against the edition's own body, as deep-dive summaries have been since v0.1.9 (consistency.check_briefing). A figure belongs to its whole story, so a line can name the company in its lead. A sentence that ties a figure to the wrong company, or says something wasn't disclosed when the body gives it, is dropped.
  • Across days (flag): a "not disclosed" claim is compared with the previous 14 editions and flagged for review if an earlier day gave the figure for the same company.
  • The "not disclosed" test is stricter everywhere: a question asking for a figure, or a sentence saying it's lacking, no longer counts as giving it, and it must be about the same company.
  • ./np consistency [DAY|all] (also a run-queue recipe) runs the checks over published editions as a dry run. Over all 18 editions and 8 deep dives it found one misattributed figure (10-22's day in brief) and two cross-day flags (10-23).

v0.1.13-beta · 2026-10-23

  • Fix: the run queue's launchd tick never started a job. Its quick idle check listed both queue folders with ls, which fails whenever one of them is empty. It now checks each file, and a test runs the real ./np runner tick.

v0.1.12-beta · 2026-10-23

  • Run queue: releases, corrections and checks can be started from the Claude chat instead of pasted into a shell (pipeline/runner.py, ./np runner, docs/plans/run-queue.md). Claude queues a named recipe and the Mac runs it. There are three tiers: tests, staging and verify run at once; corrections and publish need Steven's yes in the chat; releases, rollbacks, approvals and the public code push need Approve in a dialog on the Mac. The click grants presence for that job only (pipeline/presence.py), and no file can stand in for it. Release invariant 10 guards the runner. One-time setup: ./np runner install.
  • Docs stay current: release-gate tests now require every public module to be described in a hand-written doc and every diagram to be used. Each release lists the modules that changed while their docs didn't ("docs to review"), in the approval dialog and in data/state/docs-impact.json, for a weekly docs refresh.
  • Docs: Fact checking is rewritten as "Grounding and fact checking": six layers, a new diagram, why the first-lines check exists, corrections and known gaps. Architecture gains sections on grounding, the run queue (with a diagram) and keeping docs current, plus every smaller module.

v0.1.10-beta · 2026-10-23

v0.1.9-beta · 2026-10-23

Fix: on 2026-10-23 the deep dive's body was correct, but its summary and "Why today" lines, which readers see first in the email, on the site and in the podcast notes, said a legal-AI company disclosed no ARR and that "a vendor" claimed a $21M saving. In fact the company disclosed ARR, and the $21M was an investor's post about a different company. The day before, an unsourced Agenda line had called that investor the other company's "founder". - The why-today line comes from the checked body: it's written from the deep dive's checked "why today" section, no longer copied from the previous day's topic suggestion. - A header check (pipeline/consistency.py) for the summary and why-today lines: a sentence is dropped if a figure isn't in the checked body, if it names none of the companies or people the body ties that figure to, or if it says something wasn't disclosed when the body or a source gives it. Spelled-out figures in scripts count. If nothing in the summary survives, the checked opening is used. - Agenda lines can't assert unsourced roles: "founder", "CEO", "investor in" and similar must appear in the item's own source text; otherwise the line becomes neutral. - Deep-dive text is guarded like the briefing: a shipped deep dive changes only through a correction, and its page shows the correction note. - ./np correct DAY "what changed": records a hand edit to a shipped edition as a correction, shown on the day page and the deep-dive page.

v0.1.8-beta · 2026-10-23

Fix: the 2026-10-23 edition was held at 05:26 and again at 06:30. The release gate re-ran the whole test suite during the morning run, and one release test that checks for a running daily run saw the real one and failed. The same check blocked the backup's git push. - Released code isn't re-tested in the morning: once a code and settings fingerprint has passed the full gate (tests included) and is approved, later checks accept it without re-running the tests (data/state/release-passed.jsonl). Changed code is still fully checked. - Tests never read the live machine: test runs set NP_TESTING=1, run_in_progress doesn't look at real processes under it, and the release tests mock it too. - The evening preflight tests tonight what runs tomorrow: if the code hasn't passed the full gate yet, the preflight runs it at 20:30 and emails the owner if it fails, instead of finding out at 05:00. - The pre-push hook uses the same fast check (--release-check require), and ./np release reinstalls the hooks.

v0.1.7-beta · 2026-10-22

Shipped editions don't break. Once a day's email has gone out, that day is shipped (pipeline/shipped.py), and: - Publish guard: before every production publish, the new site is checked against what readers already have. It refuses (the live site is untouched and the owner is emailed) if any of these hold: - a shipped day page or deep dive is missing; - a shipped edition's text changed without a correction; - a shipped MP3 inside the retention window is missing; - the home page or a feed is missing, or the podcast feed would shrink. - Corrections are explicit: rebuilding a shipped day (rebrief, reprocess, remaster) needs --correct "what changed", and the page shows "Corrected <date>: …". - Remasters keep the old audio: the earlier MP3 is carried over from the live site, so no audio URL breaks. - After-publish check: once the site is live, the newest shipped pages, both feeds and the latest MP3 must answer. If not, the previous site is put back automatically, the email is held, and the owner is emailed. ./np publish restore does the same by hand. - The email waits for a good publish: if the publish fails or the after-publish check fails, no subscriber email goes out. Before, it went anyway. - Audio retention: 30 days on the site and in the podcast feed, up from 14. 60 days would be about 1 GB, the GitHub Pages limit. - Slack: links any member posts in the team channel now count, links only. Who posted is never stored, and their text is never used. - Staging preview: carries only the newest day's audio. The first full preview push timed out. - Site pushes are sturdier: a push that stalls (under 1 KB/s for 60 s) fails and is retried once over HTTP/1.1, instead of hanging the morning run. Pushes no longer use one huge buffered upload, which is what GitHub was timing out with HTTP 408.

v0.1.6-beta · 2026-10-22

  • Development preview: ./np staging publish [setup] publishes the dev checkout's site to its own Pages repo (sgwoods/ai-briefing-staging). The preview has a banner on every page linking back to the published site, is kept out of search engines (noindex, robots.txt), and has no subscribe form and no podcast feed. Staging can publish only there, and production never publishes there.
  • ./np staging compare [DAY]: staging against production for the same day: sections, counts, words, source links, the evidence mix, fact-check counts and audio length, plus the privacy scan of the preview and a diff of the edition. Writes logs/compare-DAY.md and flags what needs review.
  • Fix: a staging run no longer copies its MP3 into the owner's iCloud folder. The first staging run had overwritten that day's copy. It no longer deletes iCloud files either.
  • Tests always run as production (NP_ENV=production), in either checkout.

v0.1.5-beta · 2026-10-22

  • Fix: the scheduled jobs had been firing exactly one hour early every day (the 05:00 run started at 04:00, the 20:30 preflight at 19:30). launchd now only ticks every half hour, and the Mac's own local clock decides when a scheduled time has come (pipeline/schedule.py, ./np scheduled). Times must be on :00 or :30.
  • Releases refuse checkout-local files (.venv, .env, .staging) committed on dev; .venv is ignored as a link too.
  • Fix: rebuilding an edition (./np rebrief, ./np staging run) failed with KeyError 'critique', because the evidence check on Must reads needs the critique model, and a rebuild had stopped loading it. Found by the first staging run.
  • Git safety: every git call in the export, hub, dev and release code ignores GIT_DIR / GIT_WORK_TREE from the environment, and the tests that build throwaway repositories clear them. A leaked GIT_DIR once pointed a test's git init at the production repository and wrote a wrong core.worktree into its config. Caught and fixed before any run used it.
  • The first release built on dev and promoted with ./np release.

v0.1.4-beta · 2026-10-22

  • Development checkout: ./np dev setup creates a second working copy of the repository on branch dev, in staging mode. Inside it:
  • ./np staging sync brings in production's latest data and fixes;
  • ./np staging run [DAY] rebuilds an edition with the development code while outbound stays off, and --email sends the review copy to the owner only;
  • ./np staging reset throws away what staging wrote.
  • Staging outputs can't be committed: the pre-commit hook refuses data paths in a staging checkout, archive commits are skipped there, alerts aren't sent, and services can't be installed. Staging runs keep out of the 03:30–08:30 production window.
  • Releases and rollback:
  • ./np release VERSION "reviewed: ..." merges dev into production between 08:30 and 20:00, needs one approval, then tags the release and pushes the public code, the backup and the hub status. It refuses if production has stray code changes, a run is in progress, dev's version or changelog don't match, or the staging marker was committed.
  • ./np rollback "reviewed: ..." returns the code to the previous release.

v0.1.0-beta · 2026-10-22

The system as it runs today, labelled the first beta: a small number of outside readers.

  • Daily edition: fetch from feeds, sitemaps, Bluesky lists, newsletters and Slack links; filter, summarize, rank, cluster into stories, critique, verify and fact-check; Top of mind, Must read, Worth knowing, Open questions.
  • Evidence-weighted sources: every source has a profile, and a Must read needs primary or reporting evidence.
  • Podcast: a ~10-minute episode read by the host, followed in the same episode by the day's deep dive.
  • Public site, podcast feed and RSS on GitHub Pages; a subscriber email sent after the site is live.
  • Release gate on every outbound step: tests, secret scan, privacy invariants and Steven's approval of security-sensitive changes; owner alerts when action is needed; a cloud watchdog for missing editions.
  • Reader feedback collected from email replies and triaged daily.
  • Public code repository: an allowlisted, scrubbed export (./np push-code), MIT licence.
